Instruções para concluir o motor fiscal
1. Fechar a integração frontend → backend
Problema

O backend novo existe, mas o frontend ainda precisa parar de calcular TCO localmente e passar a consumir o motor fiscal.

Ordem para os devs
remover do frontend qualquer cálculo local de:
gross
net
credits
regra de Simples
PurchasingHub.tsx deve chamar:
POST /tax/calculate-quote
os cards da UI devem renderizar:
grossCostUnit
grossCostTotal
netCostUnit
netCostTotal
credits.icms
credits.pis
credits.cofins
credits.ipi
disallowedCredits
memory
Ação prática

Criar no frontend:

src/services/api.ts
src/services/taxApi.ts
Exemplo mínimo
// src/services/taxApi.ts
import { apiFetch } from './api';

export const taxApi = {
  calculateQuote: (payload: any) =>
    apiFetch('/tax/calculate-quote', {
      method: 'POST',
      body: JSON.stringify(payload),
    }),

  saveSnapshot: (quoteId: string, payload: any) =>
    apiFetch(`/tax/quotes/${quoteId}/tax-snapshot`, {
      method: 'POST',
      body: JSON.stringify(payload),
    }),
};
Critério de aceite

O componente PurchasingHub.tsx não pode mais ter calculateTco nem qualquer lógica local de crédito.

2. Remover do frontend a regra errada sobre fornecedor do Simples
Problema

A UI antiga bloqueava PIS/Cofins para fornecedor do Simples e mostrava mensagem fixa errada.

Ordem para os devs

Remover do frontend:

desabilitação automática dos campos de PIS/Cofins por supplier.taxRegime === 'SIMPLES'
badges/mensagens do tipo:
“Fornecedor Simples Nacional (Não gera crédito)”
Substituir por
exibição do retorno da engine:
se há crédito, mostrar valor
se não há, mostrar disallowedCredits
se há tratamento especial, mostrar memory.branches ou legalBasis
Critério de aceite

A UI nunca mais deve afirmar regra fiscal por conta própria.

3. Implementar branch real para ICMS de fornecedor do Simples
Problema

No commit, o IcmsCalculator apenas registra LC 123/2006 Art. 23, mas continua calculando crédito cheio por fórmula genérica. Isso ainda não resolve a regra.

Ordem para os devs

Refatorar icms.calculator.ts para separar:

evaluateNormalIcmsCredit()
evaluateSimplesIcmsCredit()
Regras mínimas da V2

Quando supplier.regime === 'SIMPLES', a engine deve:

não conceder crédito cheio automaticamente
validar se a operação entra no ramo do art. 23
validar se a aquisição é para:
comercialização
industrialização
registrar motivo claro quando não houver crédito
usar memória específica da decisão
Estrutura sugerida
if (ctx.supplier.regime === 'SIMPLES') {
  return this.evaluateSimplesIcmsCredit(ctx);
}

return this.evaluateNormalIcmsCredit(ctx);
Resultado esperado

O branch do Simples deve devolver algo como:

{
  tax: 'ICMS',
  eligible: false,
  creditAmount: 0,
  disallowedReasons: ['Fornecedor do Simples exige validação específica do art. 23 e parâmetros/documento ainda não informados'],
  legalBasis: ['LC 123/2006 Art. 23']
}

Até o time implementar todos os parâmetros documentais, é melhor negar com motivo claro do que conceder crédito cheio por aproximação.

4. Endurecer validação dos DTOs
Problema

Os DTOs existem, mas ainda estão frouxos.

Ordem para os devs

Aplicar class-validator e class-transformer nos DTOs do tax engine.

Exemplo
import { IsString, IsNumber, IsOptional, IsEnum, ValidateNested } from 'class-validator';
import { Type } from 'class-transformer';
Validar pelo menos
buyerCompanyId
supplierCompanyId
item.quantity
item.unitPrice
item.itemUseType
item.creditNature
item.operationType
Critério de aceite

Payload inválido deve retornar erro 400 claro, e não cálculo parcial silencioso.

5. Parar de usar defaults silenciosos em dados fiscais críticos
Problema

Hoje buildContext() usa defaults que podem mascarar cadastro incompleto.

Ordem para os devs

No TaxEngineService, remover fallback silencioso em campos como:

pisCofinsRegime
isIcmsTaxpayer
isIpiTaxpayer
state
Nova regra

Se faltar dado fiscal crítico do comprador:

lançar erro de negócio claro
ou retornar cálculo com bloqueio explícito e aviso auditável
Exemplo
if (buyer.pisCofinsRegime == null) {
  throw new BadRequestException('Comprador sem configuração de regime PIS/COFINS');
}
Critério de aceite

O sistema não pode “inventar” contexto fiscal com defaults.

6. Corrigir a semântica do IPI
Problema

O branch de IPI ainda está simplificado demais.

Ordem para os devs

Ajustar ipi.calculator.ts para:

separar elegibilidade de cálculo
melhorar a mensagem de bloqueio
não usar texto confuso como:
IPI exige uso e consumo como INSUMO INDUSTRIAL

Esse texto está errado.

Trocar por
Crédito de IPI exige destinação como insumo industrial elegível
Critério de aceite

Mensagens fiscais devem ser tecnicamente coerentes.

7. Melhorar PIS/Cofins sem travar a entrega
Problema

PIS/Cofins já melhorou, mas continua numa V1 simplificada.

Ordem para os devs

Manter a V1, mas marcar claramente o escopo:

Implementar agora
NON_CUMULATIVE obrigatório
bloqueio por:
monofásico
alíquota zero
suspenso
naturezas aceitas:
INSUMO
FREIGHT
DEPRECIATION
RESALE
Não prometer ainda
validação jurídica fina de insumo por essencialidade/relevância
casos especiais completos
frete com regras especiais refinadas
monofásico avançado por NCM
Ação de engenharia

Adicionar em legalBasis ou memory algo como:

versionScope: 'V1 structured estimate'
Critério de aceite

O sistema deve ser honesto sobre a profundidade da regra atual.

8. Versionar a engine corretamente
Problema

O snapshot salva '1.0.0' hardcoded no controller.

Ordem para os devs

Criar constante central:

export const TAX_ENGINE_VERSION = '1.0.0';

ou usar config/env.

Critério de aceite

Versão da engine não pode ficar hardcoded em controller.

9. Criar endpoint de reprocessamento
Problema

Já existe salvar snapshot, mas ainda falta reprocessar.

Ordem para os devs

Criar:

POST /quotes/:id/recalculate-tax
GET /quotes/:id/tax-snapshots
Função
recalcular com a versão atual da engine
salvar novo snapshot
manter histórico
Critério de aceite

Uma mesma cotação pode ter múltiplos snapshots em momentos diferentes.

10. Corrigir o fluxo de saving
Problema

Ordem para os devs

Separar no frontend e no backend:

Saving comercial
melhor oferta vs negociado
Saving fiscal
bruto vs líquido por créditos válidos
Saving total efetivo
custo final consolidado
Critério de aceite

A UI deve mostrar esses 3 números de forma separada.

Mensagem pronta para o time

O backend do motor fiscal já existe, com módulo, snapshots, DTOs e calculadoras por tributo. Agora falta concluir a integração e eliminar os atalhos antigos.

Prioridade imediata: remover o cálculo fiscal do frontend, integrar PurchasingHub.tsx ao endpoint /tax/calculate-quote e eliminar a regra visual que bloqueia PIS/Cofins para fornecedor do Simples.

Em seguida, corrigir o branch de ICMS para fornecedor do Simples, porque hoje ele só marca a base legal, mas ainda calcula crédito cheio de forma genérica.

Também é obrigatório endurecer os DTOs, parar de usar defaults silenciosos em dados fiscais críticos e criar reprocessamento de snapshot.

O sistema só será considerado pronto quando o frontend não decidir mais crédito, o backend for a única fonte de cálculo e o saving comercial estiver separado do fiscal.
